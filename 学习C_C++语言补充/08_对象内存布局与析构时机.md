# 08 · `make_shared` 出来的对象，成员在哪？析构谁先谁后？

> **记录时间**：2026-09-20
> **触发场景**：想搞清"智能指针作为成员时，内存到底怎么摆、谁先死"，
> 因为我不确定自己关于 `new` 连续内存、node 析构时成员指针是否一起被 delete 的推理对不对
> **原始疑问（自己 README 原文摘录）**：
> > "……由于我的外部 `auto node = std::make_shared<TopicPublishDemo>(...)` 创建对象的时候，
> > `pub_` 也会被创建在堆区…… 我可以说，`new` 的内存开辟是连续的空间，
> > 如果 node 被销毁，内部的临时智能指针……内存也会被 delete。所以这就是思想分歧的地方。"
> **对应源码**：`~/ros2_study_myself/w1_study_workspace/src/w1_topic_demo/src/topic_publisher_demo.cpp:20-22`

---

## 1. 一句话结论

1. `std::make_shared<Node>` 只分配**一块**内存装 Node 本体，**成员是内嵌在其中的**（实测偏移 8、24，地址连续）；
2. 但成员里那个 `shared_ptr` **指向的 Publisher 本体是另一块堆内存**（实测 `0x…3310` vs Node 的 `0x…32d0`）——
   **两块内存之间没有"连续性"关系**；
3. Node 析构时，成员 `shared_ptr` 只是让**引用计数 -1**；
   **Publisher 本体要等"最后一个持有者"释放时才析构**（实测它比 Node 活得久）。

> 一句话：**成员死 ≠ 被指对象死。**

---

## 2. 现象（实测输出，原样保留）

`/tmp/w1_mem_demo.cpp` 实跑：

```
[成员构造] marker_
[Publisher 构造] id=1 this=0x62d1d2b53310
[Node 构造] this=0x62d1d2b532d0  sizeof(Node)=32  sizeof(pub_)=16
node 对象起始 = 0x62d1d2b532d0
&node->pub_   = 0x62d1d2b532d8  (偏移 8)
&node->count_ = 0x62d1d2b532e8  (偏移 24)
pub_ 指向的 Publisher 本体 = 0x62d1d2b53310   ← 另一次独立分配
use_count = 1
---
复制一份后 use_count = 2
[Node 析构] this=0x62d1d2b532d0
[成员析构] marker_
node.reset() 后 use_count = 1 → Publisher 还活着（因为 extra 还握着）
[Publisher 析构] id=1 this=0x62d1d2b53310        ← 直到最后一个持有者释放才死
```

三条可直接读出的结论：

| 观察 | 说明 |
|---|---|
| `&node->pub_` 偏移只有 **8**、`sizeof(Node)=32` | 成员**内嵌**在 Node 对象里，不是"成员自己也在堆上单独一块" |
| Publisher 本体 `0x…3310` ≠ Node 的 `0x…32d0` | **Publisher 是另一块内存**（这里刚好挨在后面，但那是分配器顺手给的，不代表"连续"） |
| `[Node 析构]` 之后 `[Publisher 析构]` **还没出现** | 引用计数决定被指对象的析构时刻，**与 Node 的析构无关** |

## 3. 为什么会这样（原理）

### 3.1 对象布局：成员是"内嵌"的

```
        make_shared<Node>() 分配的【一块】堆内存
        ┌──────────────────────────────────────────────┐
Node* → │ marker_ (偏移 0) │ pub_ (偏移 8) │ count_ (偏移 24) │   sizeof(Node)=32
        └──────────────────────────────────────────────┘
                                     │ pub_ 里存着一个地址
                                     ▼
                        ┌──────────────────────────────┐
                        │  Publisher 本体（【另一块】堆）  │ ← 由 make_shared<Publisher> 分配
                        └──────────────────────────────┘
```

- **成员变量**（含 `shared_ptr` 自己那 16 字节：对象指针 + 控制块指针）是 Node 对象的**子对象**，
  和 Node 一起分配、一起销毁。
- **被指向的对象**（`Publisher`）是完全独立的另一次分配，**只在需要时才由指针去找它**。

### 3.2 `make_shared` vs `shared_ptr<T>(new T)`

| 写法 | 分配次数 | 说明 |
|---|:---:|---|
| `std::make_shared<T>(...)` | **1** | 控制块 + 对象一起分配（实测里 Node 与它的控制块在一起） |
| `std::shared_ptr<T>(new T(...))` | **2** | 先 `new` 对象，再分配控制块；中途抛异常时前面那块会漏 |

### 3.3 析构顺序规则

1. 先执行 `~Node()` 的**函数体**；
2. 再**按成员声明的逆序**析构成员（实测：`[Node 析构]` 之后才是 `[成员析构] marker_`；
   `marker_` 声明在最前 → 最后析构，而 `pub_` 比它先析构）；
3. 最后析构基类。

> ⚠️ 注意区分两件事：
> - **成员 `shared_ptr` 自己的析构**（它占的 16 字节随 Node 一起没）→ 只做"计数 -1"；
> - **被指对象的析构**（`Publisher` 干活的那个）→ 由引用计数是否归零决定。

### 3.4 引用计数曲线（实测）

| 时刻 | `use_count` | 谁还握着 |
|---|:---:|---|
| `node->pub_` 建好 | 1 | Node 的成员 |
| `extra = node->pub_` | 2 | 成员 + `extra` |
| `node.reset()`（Node 析构） | 1 | 只剩 `extra` → **Publisher 仍活着** |
| `extra` 出作用域 | 0 | **Publisher 析构** |

## 4. 最小复现（不依赖 ROS，可独立编译运行）

```cpp
#include <cstdio>
#include <memory>

struct Publisher {                       // 模拟 rclcpp::Publisher
    int id;
    explicit Publisher(int i) : id(i)
    { std::printf("   [Publisher 构造] id=%d this=%p\n", id, (void*)this); }
    ~Publisher()
    { std::printf("   [Publisher 析构] id=%d this=%p\n", id, (void*)this); }
};

struct Marker {                          // 只为“看见”成员自身的析构时机
    const char * name;
    explicit Marker(const char * n) : name(n) { std::printf("   [成员构造] %s\n", name); }
    ~Marker() { std::printf("   [成员析构] %s\n", name); }
};

struct Node {                            // 模拟 rclcpp::Node 的子类
    Marker                     marker_;  // 声明在最前 → 最后析构
    std::shared_ptr<Publisher> pub_;     // 成员只是“智能指针对”(16B)，Publisher 本体不在这里
    long                       count_;
    Node() : marker_("marker_"), pub_(std::make_shared<Publisher>(1)), count_(0)
    {
        std::printf("   [Node 构造] this=%p sizeof(Node)=%zu sizeof(pub_)=%zu\n",
                    (void*)this, sizeof(Node), sizeof(pub_));
    }
    ~Node() { std::printf("   [Node 析构] this=%p\n", (void*)this); }
};

int main()
{
    auto node = std::make_shared<Node>();
    auto * base = reinterpret_cast<unsigned char *>(node.get());

    std::printf("node 对象起始 = %p\n", (void*)base);
    std::printf("&node->pub_   = %p (偏移 %ld)\n", (void*)&node->pub_,
                (long)(reinterpret_cast<unsigned char *>(&node->pub_) - base));
    std::printf("&node->count_ = %p (偏移 %ld)\n", (void*)&node->count_,
                (long)(reinterpret_cast<unsigned char *>(&node->count_) - base));
    std::printf("pub_ 指向的 Publisher 本体 = %p  ← 另一次独立分配\n", (void*)node->pub_.get());
    std::printf("use_count = %ld\n", node->pub_.use_count());

    {
        std::shared_ptr<Publisher> extra = node->pub_;      // 复制一份 → 计数 +1
        std::printf("复制一份后 use_count = %ld\n", node->pub_.use_count());
        node.reset();                                      // 模拟：节点被销毁
        std::printf("node.reset() 后 use_count = %ld → Publisher %s\n",
                    extra.use_count(), extra ? "还活着（extra 还握着）" : "没了");
    }                                                      // extra 出作用域 → Publisher 才析构
    return 0;
}
```

编译与运行：

```bash
g++ -std=c++17 -Wall -Wextra -o /tmp/w1_mem_demo /tmp/w1_mem_demo.cpp && /tmp/w1_mem_demo
```

实测输出见本文 §2（地址/偏移/`use_count`/构造析构顺序都在那里）。

## 5. 要不要 / 什么时候 care（判断标准）

| 场景 | 要不要关心布局 / 析构时机 |
|---|---|
| 日常写 ROS2 节点 | **只需要记住结论**：句柄存成成员、成员随对象一起死、被指对象看引用计数 |
| 出现"对象还在但却不能用了" | 要：多半是"你持有的是**副本/引用**，而真正的所有者已经销毁" |
| 回调里能不能用 `this` | 要：见 `05_shared_from_this与bad_weak_ptr.md`（常驻节点捕获 `this` 就够） |
| 内存优化（嵌入式 / 大量小对象） | 要：`make_shared` 少一次分配、少一次指针跳转，缓存更友好（这点在 STM32 上也成立） |
| 想看"谁先死" | 给成员加打印（本文 `Marker` 就是干这个的） |

## 6. 逐条批改（我自己 README 里的三个推理）

| 我原来的说法 | 判定 | 修正 |
|---|---|---|
| "`pub_` 也会被创建在堆区" | ✅ **对** | 因为 Node 本体由 `make_shared` 建在堆上；`pub_`（16 字节 `shared_ptr`）**内嵌在 Node 内部**（实测偏移 8） |
| "`new` 的内存开辟是连续的空间" | 🟡 **半对** | **一个对象内部**的成员连续内嵌（偏移 8 / 24）；但 **Publisher 本体是另一块内存**，两块之间**没有连续性关系** |
| "node 被销毁，内部的智能指针内存也会被 delete" | ✅ 成员自己会析构 / ❌ 但**被指对象不一定跟着死** | 成员 `shared_ptr` 析构 = **计数 -1**；`Publisher` 要等**最后一个持有者**释放才 delete（实测 `[Node 析构]` 之后它仍活着） |
| "如果做成堆区的指针，就会造成内存浪费" | 🟡 方向对、理由不准 | 真正的理由是**所有权语义 + 异常安全**；而且 `make_shared` **更省**（一次分配装下控制块与对象） |

> 💡 这次暴露的真正短板不是"记不住规则"，而是**把"成员"和"成员指向的东西"混成了一件事**。
> 以后判断任何生命周期问题，先问一句：**"我现在说的是这个对象本身，还是它指向的那个对象？"**

## 7. 口诀 & 排查清单

### 口诀

> **"成员内嵌在对象里，指针指向的东西在别处；成员死 ≠ 被指的活物死。"**

### 排查清单

| # | 问题 | 怎么查 |
|:---:|---|---|
| 1 | 成员占多少？在对象内部哪个偏移？ | `sizeof(对象)` / `&obj.member - (unsigned char*)&obj` |
| 2 | 被指对象在哪？ | 打印指针值（`%.get()`），看是否在对象地址附近 |
| 3 | 谁在持有？还有几个？ | `use_count()` |
| 4 | 谁先析构？ | 在构造/析构里加打印（本文 `Marker` 的做法） |
| 5 | 为什么对象"还在"却不好用？ | 检查是不是**副本/引用**还在、真正的所有者没了 |

## 9. 一句话复述（自测用，能背下来才算过）

> `make_shared<Node>` 只有**一块**内存，成员**内嵌**在里面（地址连续、偏移很小）；
> 成员里那个 `shared_ptr` **指向的对象在另一块内存**，两者没有连续关系；
> Node 析构 = 成员的 `shared_ptr` 析构 = **计数 -1**，
> **被指对象要等最后一个持有者释放才死** —— 所以"成员死"和"被指对象死"必须分开谈。
